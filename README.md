# trykerja.com

The Kerja website: four static pages (Welcome, How it works, Our promise, Join the beta), the same four in Indonesian under `/id/`, and a 404 page. Plain HTML and CSS, and three scripts: `assets/site.js` for the mobile menu, the steps of Welcome's map story, the link counts and the statistics opt-out, `assets/apply.js` for Join the beta's application form, and `assets/umami.js`, our pinned copy of Umami's tracker. No build step, no packages, no cookies. Umami counts visits and a few taps (see Website statistics). The only storage kept is `umami.disabled` in `localStorage`, written only when someone opts out (`site.js` also writes and at once removes a test key, to check that storage works before Umami may load). Two requests go to other sites: the counts, to Umami's collector, and the beta application, sent to Kerja's Supabase function when someone taps Send (see below).

Ready for GitHub Pages: deploy from branch `main`, folder `/ (root)`. Pages builds it with Jekyll, which copies the pages as they are (none has front matter) and, by `_config.yml`, leaves this README and `tools/` off the site (see Security, below).

## Switch the Join the beta page's state

In `download/index.html` and `id/download/index.html` (change both), the `<body>` tag carries the state. It is the only line to change:

```html
<body data-beta="open">
```

- `open` (the default): "The Canggu beta is open. Install in two steps." with the two steps and the TestFlight invite button (and the QR code on a computer)
- `full` (the state today): "The Canggu beta opens soon." with the beta application form in the invite's place (and the QR code to this page on a computer)

Only one state is ever shown. The full state's lines also carry the `hidden` attribute, so leave it on them: `data-beta="full"` is what shows them.

## The beta application form (decisions 5289, 5290)

In the `full` (opens soon) state, `/download/` and `/id/download/` carry one form, `#apply`, where the invite is in the `open` state; On Android's "Go to the form" links to it. The fields, and nothing more: first name, email, which fits you best (Founder, Content creator, Freelancer, Other), how long you're in Canggu (Just arrived, 1–3 months, I live here), one optional Instagram or LinkedIn link, one optional line ("What would you work on next to someone?"), the "I'm 18 or older" and privacy policy ticks, and a hidden honeypot, `website`, which must stay empty. No age, no photo, no phone number.

`assets/apply.js` checks the fields as the function does and sends them as JSON (`lang` from `<html lang>`) to the form's `data-endpoint`, per the contract in `kerja-artifacts/beta-apply/contract.md`. Each field the page or the server (a 400's `fields`) refuses gets its line under it, `aria-invalid`, and a link in the box above the fields, which takes focus. A 429 shows "Too many tries for now"; a 403 (an `Origin` the server doesn't allow), a 500, a 400 without a usable `fields` list, or no answer "Your application didn't go through"; both with hello@trykerja.com. Whatever the answer, Send comes back (the sites audit's A4). The link is sent as typed, normalized only as the contract's "link field" says (decision 5301): starting with `@`, unchanged; with a `.` or a `/`, `https://` added when there is no scheme; a bare word gets `@` (an Instagram handle). Whether it is an Instagram or LinkedIn profile is the server's call (its 400 shows the field's line). A 200 replaces the form with "You're on the list." by first name. Without JavaScript, the form is hidden and a line says to email hello@trykerja.com; the Send button stays disabled until the script is ready, so the form is never sent any other way. In a frame on another page, `apply.js` does nothing, so Send stays disabled there too (the sites audit's A6). Every word is in the page, in its language; the script holds none. No cookies, and the form keeps nothing in the browser. Umami counts visits and a few taps (see Website statistics); from the form, only `apply-sent` or `apply-error` with the answer's kind, never a field. The only storage kept on the site is `umami.disabled`, written only when someone opts out.

The form replaced the waitlist (its `mailto:` buttons, the Copy button and the "No email app?" panel). No page has a `.waitlist` block any more, so `site.js` has neither the Copy code nor site-waitlist's mailto handler (decision 5348), which had nothing left to act on (decision 5372).

**The endpoint.** Both pages post to **kerja-prod's** function: `data-endpoint` is `https://eppqufcgcwhoprwzfhxy.supabase.co/functions/v1/submit-application` (decision 5360, the sites audit's A1), the one address the two pages' `connect-src` allows (see Security, below). kerja-prod answers only `https://trykerja.com`, in CORS and on the server, which refuses any other `Origin`, or none, with a 403 (decisions 5301, 5360). kerja-dev's function was used for the G1 tests only; its URL is in no file here, and `tools/csp_check.py` fails if its project ref ever shows up in a published file. Previews never post to Supabase: they use the local mock (below).

**The local mock.** `python3 -I tools/apply_mock.py --port 8091` serves the site on http://127.0.0.1:8091/ and answers the contract at `/functions/v1/submit-application` (standard library only). In the pages it serves, and only there, `data-endpoint` becomes `http://localhost:8091/functions/v1/submit-application` (another origin, so the browser's CORS preflight runs as it will against Supabase), and so does kerja-prod's function in the CSP's `connect-src` (the sites audit's A3), so the page's own policy lets the preview's request through; nothing in a published file changes for it. A valid application gets 200; a filled honeypot 200 (dropped); a refused field 400 with `fields`; an `Origin` other than `http://127.0.0.1:<port>` or `http://localhost:<port>` 403. The email's local part shows the other answers: `toomany@…` 429, `origin@…` 403, `broken@…` 500, `offline@…` no answer at all. It logs statuses and field names only. Use a plain static server (`python3 -I -m http.server`) to see the pages as they are.

## Website statistics (Umami Cloud, decisions 5401 to 5407)

Page views and a few named clicks are counted with **Umami Cloud** (Umami Software, Inc.), on its free Hobby plan, without cookies. The auditor approved the plan and wrote the words (decisions 5409, 5412); Zayd created the account himself (5421). Nothing is published before Zayd's own line. The record, with the research and the checks, is `kerja-artifacts/site-analytics/record.md`.

**The tracker is our own copy** (decision 5407, the auditor's choice): `assets/umami.js`, served from trykerja.com and never loaded from Umami's servers, so `script-src` stays `'self'` and no code from another site runs on the pages. It is byte for byte the tracker of one Umami release, and is never edited:

- **Umami 3.4.1** (released 23 October 2026): `/app/public/script.js` in Umami's official image `ghcr.io/umami-software/umami:3.4.1` (index `sha256:e69d1a7932e9dab0fc523edc7be1f3a53f3c261f57856fc2167ae74a8fc022e8`; its linux/amd64 and linux/arm64 builds are the same bytes), built from https://github.com/umami-software/umami/blob/v3.4.1/src/tracker/index.ts. Umami's GitHub releases carry the source only; the image is where the release's built tracker is.
- 4,773 bytes, **SHA-256 `654f12c7548be726eba5b71d5ef8bffc2a41a39a0053e2a49a847869ccd7ac3f`**.
- MIT licence, Copyright (c) 2022 Umami Software, Inc.: `assets/umami-LICENSE.txt`, published beside it (the minified file carries no notice, and can't be edited to add one).

`tools/csp_check.py` holds that SHA-256 (`UMAMI_SHA256`) and fails if the file changes by one byte. `python3 -I tools/umami_fetch.py 3.4.1` downloads the release's file again from ghcr.io (GitHub's registry; never Umami's collector) and says whether ours is the same bytes.

**The loader: Umami only where the visitor's choice can be kept** (decision 5431, the auditor's fix B: fail closed). No page carries the tracker's tag. `site.js` adds it, after handling the `#kerja-me` marker, only if this browser's `localStorage` can be written, read back and cleared (a test key, `kerja.storage-check`, removed at once) and the visitor hasn't opted out (`umami.disabled` not set). If any step throws or reads back wrong, nothing is loaded, so nothing is counted: with storage blocked, with JavaScript off, or if `site.js` fails, `umami.js` isn't even fetched. The tag it adds sits beside `site.js` in `assets/` (same origin, so `script-src 'self'` covers it):

```html
<script src="…/assets/umami.js?v=654f12c7" defer data-website-id="b33e8625-5183-4fd3-973d-9e1feb90f868" data-host-url="https://gateway.umami.is" data-do-not-track="true" data-domains="trykerja.com" data-exclude-search="true" data-exclude-hash="true"></script>
```

Its path, stamp, website ID and six attributes are in one place, `TRACKER` in `site.js`; `tools/stamp.py` keeps its `?v=` current. `tools/csp_check.py` checks every value there, pins the loader (the `[tracker-loader]` block, `LOADER_SHA256`: change it on purpose only, re-test, then update the pin), and fails if a page carries a static tracker tag or anything else creates a `<script>`.

- `data-website-id`: **`b33e8625-5183-4fd3-973d-9e1feb90f868`**, the trykerja.com website in Zayd's Umami Cloud account (Hobby, EU; decision 5421), on all nine pages. It is public by design, not a secret. `csp_check.py` fails if a page carries any other ID (`UMAMI_WEBSITE_ID`), and `--publish` also if one carries the old placeholder `00000000-0000-0000-0000-000000000000`.
- `data-host-url`: Umami Cloud's collector, `https://gateway.umami.is` (the tracker posts to `/api/send` there). Without it, this build would post to `/assets/api/send` on trykerja.com.
- `data-do-not-track="true"`: a browser that sends Do Not Track sends nothing.
- `data-domains="trykerja.com"`: the tracker sends only from `trykerja.com` (www.trykerja.com redirects there), so previews (127.0.0.1, localhost, `apply_mock.py`) and copies on other hosts never send anything.
- `data-exclude-search="true"` and `data-exclude-hash="true"`: the page's address and the referrer are sent without their `?…` and `#…` (so no campaign tags, no `fbclid`, no `#apply`, no `#kerja-me`).
- Nothing else: no `data-performance` (web vitals), `data-tag`, `data-distinct-id` (`umami.identify` is never called), `data-before-send` or `data-auto-track`. `csp_check.py` fails on any other attribute in `TRACKER`.

**What it sends.** Once the page has loaded, one page view; on a tap on a counted link or the menu button, one event. Each is one `POST https://gateway.umami.is/api/send`, without credentials, with the headers `Content-Type`, `x-umami-website-id`, `x-umami-hostname` and, after Umami's first answer, `x-umami-cache` (a token from that answer, kept in the page's memory only). The body is `{"type": "event", "payload": {…}}` with `website` (the ID), `hostname` (`trykerja.com`), `url` (the page's address, for example `https://trykerja.com/id/download/`), `title` (the page's title), `referrer` (where the visitor came from, as the browser gives it: from another site, what that site's policy allows, usually its origin; between our pages nothing, as every page is `no-referrer`), `screen` (the screen's size, for example `390x844`) and `language` (the browser's, for example `en-US`); an event adds `name` and `data` (the element's `data-umami-event-*` words, or the form's `kind`). The request also carries what every request carries: the IP address and the browser's User-Agent. The tracker writes no cookie and nothing to `localStorage` or `sessionStorage`; it reads one `localStorage` key, `umami.disabled` (below). It never reads the form, and nothing a visitor types is ever passed to it.

**A tap never waits for Umami** (Q535, decision 5409). Umami's own `data-umami-event` on a link holds the tap until the collector has answered, then opens the link itself (Umami 3.4.1, `src/tracker/index.ts:349-365`), so no link carries it. A link carries `data-count="<event>"` (and `data-count-at`, `data-count-lang`) instead: `site.js` hears the click and calls `umami.track(event, data)`, which starts its request at once with `fetch`'s `keepalive`, so it can finish after the page has gone (`index.ts:384-399`); it never calls `preventDefault`, and the link opens at once. A count that doesn't make it is lost rather than the tap delayed. The menu button, which opens nothing, keeps `data-umami-event="menu-open"`: Umami counts a button without holding it (`index.ts:370`). The tap measurements are in the record.

**The events,** one name in both languages. `csp_check.py` allows `data-umami-event` only as `menu-open` and never on a link, `data-count` only with the link events below, and only `at` and `lang` as data, each a short lowercase word:

| Event | Element | Where | How | Data |

| `menu-open` | the menu button (phones) | all nine | `data-umami-event`, Umami | none |

| `testflight` | "Open the Canggu beta invite" (no `href` until Apple's link) | Join the beta, `open` state | `data-count`, `site.js` | none |
| `testflight-app` | "Get TestFlight." (the App Store) | Join the beta, `open` state | `data-count`, `site.js` | none |

**Leaving Zayd's own visits out** (decision 5404). In a browser whose `localStorage` holds `umami.disabled` for trykerja.com, `site.js` doesn't load the tracker at all (and on a page already counting, the tracker reads the flag before every send). `site.js` sets it whenever a page is opened with `#kerja-me` at the end of its address, and removes it with `#kerja-me-off`; the marker then leaves the address bar. `site.js` runs before `umami.js` on every page, so the visit that carries the marker isn't counted either. The flag belongs to one browser (each app's browser is its own), so:

1. **Safari and Chrome on the Mac:** open https://trykerja.com/#kerja-me in each (and in each Chrome profile you use).
2. **Safari on the iPhone:** open https://trykerja.com/#kerja-me.
3. **Instagram on the iPhone** (its browser has no address bar): send https://trykerja.com/#kerja-me in a direct message between two accounts you use (for example yours and @trykerja), and tap it there. It opens in Instagram's browser and sets the flag for that browser.
4. **Check it:** in Umami, open the website's Realtime view, then open trykerja.com in that browser. No new visitor should appear.
5. **Do it again** after clearing the browser's website data, in each new private window (it forgets when closed), and whenever your own visit shows up in Realtime (Safari and in-app browsers can drop a site's storage after some days without a visit).

To be counted again in a browser, open https://trykerja.com/#kerja-me-off. Anyone can use the marker (the site's code is public); it only leaves that person's own visits out. (Umami's IP filters are on paid plans only.)

**The visitors' own opt-out** (decision 5412, the auditor's ruling: Safari sends no Do Not Track, and France's CNIL asks consent-free audience measurement to let people object). Our promise's last line in "Your data stays yours" (`promise/index.html:128`, `id/promise/index.html:128`), in the auditor's words (`kerja-artifacts/promise-text.md`), ends with a button: "This website has no cookies. It counts visits and a few taps, never your name, your email or what you type in the form. [Don’t count my visits]"; after the tap, "Your visits aren’t counted in this browser. [Count them again]" (Indonesian: "… [Jangan hitung kunjunganku]", "Kunjunganmu tidak dihitung di browser ini. [Hitung lagi]"). `site.js` sets or removes the same `umami.disabled` flag as `#kerja-me` / `#kerja-me-off`, swaps the line only once the flag has been saved and read back (moving focus to the other button), and opens the page on the line that matches the flag. The buttons are real `<button type="button">`s, in the page's link style (`.pr-optout-btn` in `promise.css`), and carry `hidden` in the page: without JavaScript, or where `localStorage` can't be written and read back (the loader's own test, so nothing is counted there either), only the first sentence shows, with no button, so the page never offers what can't work. Nothing on, around or in the line carries `data-count` or `data-umami-event`, so a tap sends nothing (`csp_check.py` fails otherwise); it writes nothing but the flag.

**Updating the tracker** (on purpose only; the copy is never edited by hand):

1. Pick a release at https://github.com/umami-software/umami/releases and read what changed in the tracker since ours: https://github.com/umami-software/umami/compare/v3.4.1...v<new> (`src/tracker/` and `rollup.tracker.config.js`). It must still send only to `data-host-url`, write no cookie or storage, read no form, and give the attributes above the same meaning.
2. `python3 -I tools/umami_fetch.py <new> --write` (it prints the size and the SHA-256). With Docker instead: `docker create --name umami-tracker ghcr.io/umami-software/umami:<new>`, `docker cp umami-tracker:/app/public/script.js assets/umami.js`, `docker rm umami-tracker`, then `shasum -a 256 assets/umami.js`.
3. Put the new SHA-256 and version in `tools/csp_check.py` (`UMAMI_SHA256`, `UMAMI_VERSION`) and in this section, and run `python3 -I tools/stamp.py` (it updates `TRACKER.src` in `site.js`, then the pages' `site.js` stamps).
4. Run `python3 -I tools/csp_check.py` and `python3 -I tools/stamp.py --check`, then the record's preview checks (Chrome, with the collector answered locally).

**Previews never count.** `data-domains` keeps every preview silent (`python3 -I -m http.server`, `tools/apply_mock.py`). The checks that need payloads serve a copy whose `site.js` has no `data-domains` and answer the collector inside Chrome (DevTools' `Fetch` domain), so no request reaches Umami.

## Cache-busting

Every picture, stylesheet and script URL in the pages (the English ones, the 404 and the four under `/id/`) carries `?v=` and the first 8 characters of the file's SHA-256, so a changed file always gets a new URL. The statistics tracker's stamp is in `assets/site.js` (`TRACKER.src`), which adds it. After changing any of them, run `python3 -I tools/stamp.py` (and `python3 -I tools/stamp.py --check` lists every URL and fails if one is stale or missing).

## The map story (Welcome, desktop only)

On a screen 1024 px wide or more, with motion allowed, Welcome shows a flat map of Canggu between the hero and "A morning on Kerja": sample people checked in at cafés, a session card and a chat with Nico come in as four short lines scroll past (`.story` in `index.html` and `welcome.css`, the steps in `site.js`). Below 1024 px, or with reduced motion, it isn't shown and the page is as before.

The map is the app's opening view (decisions 5249, 5250, 5256): zoom 15 in the app's projection, a 640 × 620 window, 1 px = 1 app point. The café pins are drawn as the app's map draws them (the orange pill with the cup and up to three faces then "+N", the quiet white cup, the ink "+N" badge for cafés a pin hides, the name under the pointer), with the app's own rule for which pins are drawn and which are counted. On a narrower map the pins keep their size and the rule runs again for that scale (container queries in `welcome.css`). Faces are cast-v3 portraits only, whole, as the app's avatar shows them (`assets/story/face-<first name>-2x.webp` and `-3x.webp`, 52 and 78 px, made with `sips -z` and `cwebp -q 86 -m 6 -sharp_yuv`). The cafés' names are never page text: they are drawn into an image (`assets/story/pin-names-2x.webp` and `-3x.webp`), and the pins, faces and names are hidden from screen readers; the map's one alt is "Illustration of sample profiles checked in at cafés in Canggu".

`tools/draw_map.py` makes all of it: the drawing `assets/story/canggu-map.svg` (our own drawing of OpenStreetMap data: roads, water, in the app's map colours, with no names, cafés or buildings), the pins between the `pins` comments in `index.html` and `id/index.html` (the window, who is where, which pins are drawn) and in `welcome.css` (the narrower maps), and the names' image (with headless Chrome and `cwebp`). The data is one Overpass download for the box lon 115.112 to 115.160, lat -8.672 to -8.626; it is ODbL and stays out of this repo (it's kept with its query and download time in `kerja-artifacts/build-12/scroll-story/osm/`). To redraw, run `python3 -I tools/draw_map.py <that file> <the app's docs/data/canggu-cafes.csv>`, then `python3 -I tools/stamp.py`. The page makes no call to any map service.

"Sample profiles and sessions. An illustration, not live activity at these cafés." and "© OpenStreetMap contributors" (linked to https://www.openstreetmap.org/copyright) are on the map's top left and again just under its bottom edge, so one of each is fully on screen whenever any of the map is: while the map comes in from below, the top note rides the screen's bottom edge just above the map; while it leaves at the top, the copy under its bottom edge is on screen.

## The domain

## Where things are

## Security

The security audit of 28 October 2026 (decisions 5329 to 5334). Every finding, with its severity and whether it is done, is in `kerja-artifacts/sec-audit/sites.md`.

**The Content-Security-Policy.** Every page carries these two tags right after the viewport tag, before anything it loads:

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'; style-src 'self' 'sha256-ftlsA0RZH98RbIQI+AjVCQ3J902Of/2USl+6/hI5cNg='; img-src 'self' data:; font-src 'self'; connect-src 'self' https://gateway.umami.is/api/send; form-action 'none'; base-uri 'none'; object-src 'none'">
<meta name="referrer" content="no-referrer">
```

- `script-src 'self'`: `assets/site.js`, `assets/umami.js` (our pinned copy of Umami's tracker, added only by `site.js`'s loader; see Website statistics), and on Join the beta `assets/apply.js` too. No inline script, no `on…=` attribute, no `eval`, no `javascript:` link.
- `style-src 'self'` and one hash: the stylesheets in `assets/`, and the one inline block, `<noscript><style>.menu-btn,.copy-btn{display:none!important}</style></noscript>` (it only applies with JavaScript off). Change that block and its hash must change with it. **Join the beta** (`download/`, `id/download/`) has its own block, `<noscript><style>.menu-btn,.apply-form{display:none!important}</style></noscript>` (with JavaScript off the form is hidden and the line to email hello@trykerja.com shows), so its hash is `'sha256-blf9WhBRk+NXh0prSpGNj34q3s6bpj4diqnfCnS1rmI='` in place of the one above (decision 5360, the sites audit's A2). The seven other pages keep `.copy-btn` in theirs although no page has a Copy button any more: left as it is, so their pages and hash don't change.
- **Welcome only** (`index.html`, `id/index.html`) adds `style-src-attr 'unsafe-inline'`, for the map story's 13 `style=""` attributes that `tools/draw_map.py` writes (each pin's `--x`, `--y` and `--more`, the pills' widths, the names' offsets). It is the only `unsafe-inline`: style attributes on those two pages, never a script or a `<style>` block.
- `img-src 'self' data:`: the pictures in `assets/`, and the 1 × 1 GIF in two `<picture>` fallbacks (Welcome's hero phone under 600 px, the story's map under 1024 px or with reduced motion).
- `font-src 'self'`: the WOFF2 files in `assets/fonts/`.
- `connect-src 'self' https://gateway.umami.is/api/send`: Umami Cloud's collector, exactly that address (not the whole origin: Q534, decision 5409), where `assets/umami.js` posts page views and events (decisions 5402, 5407; see Website statistics). `'self'`: no page fetches anything from its own site, but Chrome's DevTools and Lighthouse fetch through the page (DevTools' `/.well-known/appspecific/com.chrome.devtools.json`, Lighthouse's `robots.txt`); with `'none'` those showed as CSP violations in the console whenever DevTools was open and failed Lighthouse's robots.txt audit (SEO 100 to 92). **Join the beta** (`download/`, `id/download/`) also allows exactly one more address, kerja-prod's function `https://eppqufcgcwhoprwzfhxy.supabase.co/functions/v1/submit-application`, the form's endpoint (see above), between `'self'` and the collector. Never kerja-dev's.
- `form-action 'none'`, `base-uri 'none'`, `object-src 'none'`: no form is ever submitted by the browser itself, no `<base>`, no plugins.
- `no-referrer`: no page needs a `Referer`. A `fetch` to another site still carries the page's `Origin` (checked in Chrome and Safari), which is what the beta function checks.
- A meta tag can't carry `frame-ancestors`, `report-uri`, `report-to` or `sandbox`, so none is there (browsers would ignore them and log a warning).

**After changing any page,** run `python3 -I tools/csp_check.py` (or `python3 -I tools/csp_check.py <folder>`; it walks the folder, so it needs no git checkout and sees new, uncommitted pages). It checks what Pages would publish (the rule below) and fails when a page hasn't exactly one CSP meta and one referrer meta before anything it loads; when the referrer isn't exactly `no-referrer`; when the CSP isn't exactly the one above for that page, directive by directive and in that order (style-src lists the hash of each of the page's own inline `<style>` blocks, and none if it has none; Welcome adds `style-src-attr 'unsafe-inline'`; Join the beta adds kerja-prod's function to `connect-src`; every page ends `connect-src` with Umami's collector URL), so any other source, keyword or directive fails; when a page has an inline script, an `on…=` attribute or a `javascript:` URL, style attributes anywhere but Welcome (or Welcome without them), a form whose `data-endpoint` isn't kerja-prod's function, anything loaded from another site, or a `target="_blank"` link without `rel="noopener"`; when any published HTML, JS, CSS, SVG, XML, JSON or TXT file names kerja-dev's project ref, in any case; when a published stylesheet loads from another site or uses `@import`; when `assets/umami.js` isn't byte for byte the pinned Umami release (its SHA-256); when a page carries a static tracker tag, when `site.js`'s `TRACKER` config or `[tracker-loader]` block isn't the pinned one, or when anything else creates a `<script>`; and when a page has `data-umami-event` on a link (Umami would hold the tap), or an event or event data it doesn't know. It also fails when a page's website ID isn't Kerja's (`--publish` also on the old placeholder).

**What GitHub Pages can't do.** Pages sends no security headers and can't be told to (no `_headers` file, no settings): no `Strict-Transport-Security` (http:// does get a 301 to https://, as "Enforce HTTPS" is on, but browsers aren't told to remember it, and the domain can't be preloaded), no CSP header and so no `frame-ancestors`, no `X-Frame-Options`, no `X-Content-Type-Options: nosniff`, no `Referrer-Policy` header, no `Permissions-Policy`, no `Cross-Origin-Opener-Policy`. The cache is always `max-age=600`, every answer says `Server: GitHub.com` and carries `Access-Control-Allow-Origin: *`. The meta tags cover the CSP (all but `frame-ancestors`) and the referrer. The rest would need a proxy in front of Pages (Cloudflare, for example): Zayd's decision, not a change in this repo. Without `frame-ancestors`, another site can show these pages in a frame; they have no account, sign-in or button that acts for anyone, and Join the beta's form, the one thing worth framing, stays inert in a frame (`apply.js` does nothing there; Send stays disabled).

**What Pages publishes.** Pages builds `main` with Jekyll (there is no `.nojekyll`): a file without front matter is copied as it is, so every page, stylesheet, script and picture is served byte for byte; names starting with `.` or `_` are left out (`.gitattributes`, `_config.yml`); and `_config.yml` leaves out `README.md` and `tools/` (the scripts, the form's local mock among them). `theme: null` stops Pages adding its default theme (Primer) and the `/assets/css/style.css` that comes with it, which isn't in this repo (legal.trykerja.com, with no theme line, serves one). `robots.txt`, `sitemap.xml`, the favicons and the fonts' OFL licences are public on purpose, and so, probably, is `CNAME`: Pages' build leaves it out only through its default `exclude` list, which a custom `exclude` replaces (legal.trykerja.com, with no `exclude`, answers 404 for it). It only holds the domain name, and the domain works either way. Never start a file with a `---` line unless Jekyll is meant to build it. Before decision 5331, a `.nojekyll` file had Pages serve every file of the repo, so `README.md`, `tools/draw_map.py`, `tools/stamp.py`, `tools/qr.mjs`, `.gitattributes` and `.nojekyll` were all reachable on trykerja.com. (The repo itself is public on GitHub, so nothing secret was ever in them; it is about not serving notes and tools under the site's name.) If a Jekyll build ever failed, Pages would keep the last good site; putting `.nojekyll` back undoes this.

**Third parties: no code from elsewhere, two requests.** Every page loads only its own files (no fonts, scripts, styles, maps or pictures from elsewhere; Umami's tracker is our own pinned copy, `assets/umami.js`), so there is nothing to pin with Subresource Integrity. Two requests go to other sites: the counts of visits and a few taps, to Umami Cloud's collector `https://gateway.umami.is/api/send` (see Website statistics), and the beta application, to kerja-prod's function when someone taps Send. No cookies. The only storage kept is `umami.disabled` in `localStorage`, written only when someone opts out (`site.js` also writes and at once removes a test key, to check that storage works before Umami may load). The links to other sites (OpenStreetMap's copyright page, TestFlight on the App Store, WhatsApp's share link, Instagram's @trykerja page, legal.trykerja.com, `mailto:`) load nothing until clicked, and none opens a new window.

**Scripts.** `assets/site.js` and `assets/apply.js` write text only with `textContent` and never `innerHTML`, `insertAdjacentHTML`, `document.write`, `eval` or `new Function`. The `mailto:` and WhatsApp links are written out percent-encoded in the pages.
